## Problem

SGLang HiCache keeps GPU L1 KV in BF16 and, on eviction, stores that KV in the CPU L2 tier. HiQCache changes only the L2 bytes to a padded per-head INT8 record so the same host budget holds more tokens.

## Technique

Symmetric per-head absmax INT8 with a stored BF16 scale: s = max(abs(x))/127, q = clamp(round(float32(x)/float32(s)), -127, 127), restore BF16(q*s). All-zero heads use a power-of-two absmax floor (2^-112) so the scale stays a normal BF16. Each (layer, K or V, token) row is 1152 bytes: 1024 B INT8 (8 heads x 128), 16 B of eight BF16 scales, 112 B padding. Row size is a multiple of 128 so SGLang's existing CUDA JIT HiCache byte mover is unchanged. Active GPU KV, radix tree, eviction policy, and attention stay BF16.

## Foundation

Per-head symmetric INT8 plus an elementwise bound the codec checks against a float64 reference: |x_hat - x| <= (0.5 + 2^-8)*s + 2^-8*|x_hat| (INT8 rounding, BF16 scale error, BF16 output rounding). Capacity is the byte identity 2*36*2048 = 147456 BF16 bytes/token versus 2*36*1152 = 82944 encoded bytes/token, ratio 147456/82944 = 1.7778x, saving 43.75%. The 1152-byte alignment is an interface constraint of the CUDA mover, not a new cache policy.

Serving measurements in the October 2026 manifest: NVIDIA RTX A6000 (46068 MiB, sm_86), PCIe Gen4 x16, 96 vCPU, 503 GB RAM, Ubuntu 24.04, a pinned SGLang fork (sha 89e0023e215a6d80b6cff0e3075e11067f2ff90d, branch hiqcache/int8-l2), torch 2.14.1+cu130, CUDA 13.0, Qwen/Qwen3-8B BF16, TP=1, page size 1. ## Modifications

Nothing in this tree plugs into Ollama or the DRock executor. Using the idea would mean a new KV packer inside Ollama for whatever small Qwen head layout is loaded, on Arc or CPU, with no SGLang 128-byte CUDA mover. That is a different project, and the measured gain is extra CPU-L2 prefix slots on a 128-request shared-prefix serving trace, which a single local agent turn does not have.

## Limitations

Source: layout is fixed to Qwen3-8B, 8 local KV heads, head dim 128, TP=1, page size 1, BF16 GPU KV; other TP, MLA, hybrid models, and other backends are unvalidated. One 16-token greedy restore is the only completed quality check; the multi-prompt quality run failed. Elementwise error bound does not imply output equivalence. Latency is one run per replay config; TTFT was unstable across earlier pairs; p95/p99 TTFT did not improve in the replay. Microbench is standalone pinned copies, not the in-server mover, and its BF16 control is invalid. Encode/decode time is already larger than the compressed copy (15.11 ms encode and 8.46 ms decode vs 7.64 ms H2D on an A6000). Opinion: DRock's i5-8400, 32 GB, and Arc A380 6 GB cannot host this CUDA HiCache path, and a 119 s discuss-grounded turn is not the same bottleneck as a few hundred milliseconds of TTFT on prefix hits.
