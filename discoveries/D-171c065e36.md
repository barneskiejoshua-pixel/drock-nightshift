## Problem

CPU-only LLM inference is often bottlenecked by memory bandwidth, poor SIMD utilization, and per-backend/kernel tradeoffs, especially for ternary/quantized models on commodity CPUs.

## Technique

Project Zero (`pz`): a from-scratch C inference engine with one binary, no GPU/Python/third-party deps; runtime SIMD dispatch (AVX-512 VNNI/AVX-512/AVX-VNNI/AVX2/NEON/dotprod/scalar), first-run calibration, hand-written matmul kernels (ternary/Q2/Q4K/Q5/Q6K/Q8/F16/BF16), pre-quantized activation reuse across workers, block-wise INT8/INT4 classifier heads with accuracy self-check/fallback, KV-cache quantization/offload, and OpenAI-compatible serving.

## Foundation

Systems/architecture: SIMD vectorization and ISA-specific dispatch, quantized linear algebra (int4/int8/block scales, ternary {-1,0,1}), memory-bandwidth-aware kernel design, and runtime calibration/quality gating (perplexity tolerance).

## Compute

CPU inference; tested on x86-64 (AVX2 minimum for dense GGUF, x86-64-v2 for ternary). Reported benchmarks on Intel Xeon @ 2.10 GHz AVX-512 VNNI, 4 vCPU; build requires GCC/Clang+C++, make, pthreads, libm. No GPU.

## Modifications

Not a direct DRock fit: DRock uses Ollama for model inference, not a custom C inference engine. If DRock ever needed an embedded/offline CPU backend, Project Zero's runtime SIMD dispatch, calibration, and quantized-head self-check/fallback could inform design; but adopting it would mean replacing the inference stack and revalidating model behavior.

## Limitations

Different layer than DRock's agent/gate/prompt problems. Reported gains are hardware/kernel/model specific; Q4_K dense models are still slower than llama.cpp in their own report (Qwen3-8B Q4_K_M 1.6–1.9× slower). INT8/INT4 classifier lost VNNI fast path after block-wise-scale correctness fix (issue #27), trading speed for quantization quality. No evidence it addresses agent planning, verification, or false-success behavior.
