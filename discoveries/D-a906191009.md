## Problem

A persistent LLM agent that changes its LoRA adapter mid-session has two options for the cached history. It can keep the KV cache built under the old adapter, which mixes model versions. Or it can re-prefill the whole history under the new adapter, and that cost grows with history length and with the number of active sessions. The paper wants the new adapter adopted without replaying the history and without losing exactness.

## Technique

LiveLoRA is a model-runtime co-design. Only the final decoder block is adapted. Embeddings, blocks 1..L-1, all norms and the LM head stay frozen. Q, O and the MLP in the final block get ordinary LoRA (rank 8, alpha 16). K and V use LoRA-FA-style adapters: the down-projections A_K and A_V are fixed (rank 32, orthogonal init, scale 1) and only B_K and B_V train. The input to the final block therefore never changes across adapter versions. The runtime stores each token's base K/V projections plus its fixed low-rank coordinates (x A_K, x A_V). For a new adapter version it rebuilds K/V as base + coords @ B_new, runs only the latest token through the final block, and commits the adapter, the cache and the next-token logits as one atomic step. The paper calls this step publication. Training runs on a separate adapter copy, and the method does not depend on the learning rule.

## Foundation

Linearity of LoRA: K = x W_K + (x A_K) B_K. With A_K fixed and x frozen (the lower blocks are frozen), x A_K is constant per token, so new K/V are a matmul over stored coordinates. The final block is the only adapted layer, so no deeper layer's input changes, and attention over the reconstructed final-block K/V gives the same continuation as a full re-prefill. The paper proves this equivalence in exact arithmetic under those assumptions. It assumes standard RoPE, contiguous sequences and no paged cache.

## Compute

Every experiment ran on one NVIDIA H200 in BF16, with an FP32 control on one 8K history. The method needs a white-box runtime that exposes per-layer K/V tensors, plus extra per-session storage for the base projections and coordinates (9.48 MiB per 8K session in compact retention). The original study used a custom latest-token kernel. The revised runtime uses native SDPA/eager attention. The serving framework is not named.

## Reported

Qwen2.5-3B-Instruct, H200, BF16, Gaussian (not learned) adapter updates. Publication speedup over full-history re-prefill: 68.98x as the average of median paired speedups over 5 runs, 32 sessions x 8K tokens (95% CI 67.08-71.39, p5 62.96x). 51.06x for one session at 32.7K tokens. 8.79x for one session at 8K. Migration latency stays near 17.15-18.03 ms from 2K to 32.7K tokens, while re-prefill grows from 40.78 ms to 919.21 ms. Decoding overhead is 4.75-4.88% over native cached decoding and 0.68-0.81% over guarded direct serving (one session, 2K-32K). An earlier version of the study measured 19-24% decode overhead, and the paper puts the gap down to a runtime change. Storage: compact retention needs 3.42x less than retained-boundary replay at 8K (9.48 vs 32.41 MiB), and publication-plus-decoding cost lands within 0.60% of boundary replay. Total saving over re-prefill is 16.24% at update cadence 32 and 3.90% at cadence 128. Break-even is about 600 tokens per update against re-prefill. BF16 numerical error: max logit error 0.125 at publication versus boundary replay. Against full re-prefill continuation the max logit difference is 1.1875 at cadence 32 and 5.59 at cadence 128. Greedy tokens agreed in the tested cases. FP32 max logit error is 2.43e-5. A trainable-A ablation needs 4.27x the migration state and has 10.85 points more overhead. Task-level quality of the restricted adapter is explicitly not evaluated.

## Drock application

None today. DRock serves models through Ollama, whose llama.cpp runtime does not expose per-layer K/V or a LoRA hot-swap with cache migration. DRock's own native.py keeps a float32 KV cache between calls (native.py:631) and could in principle host this. But DRock's LoRA work (tools/train/train.py) trains offline in a separate venv, and adapters change between runs, never mid-session. A cold re-prefill after an adapter change happens once and is then cached as the shared prefix. The only adapter on disk (tools/train/adapters/feas-cpu-06b) targets all seven projections in every layer of Qwen3-0.6B, which breaks the final-block-only, fixed-A_K/A_V assumptions the method needs.

## Modifications

Applying it would take four changes. (1) Retrain the reflex adapter restricted to the last block, with LoRA-FA on K/V, and measure whether such a narrow adapter still moves DRock's benchmark pass count; the paper never measured quality. (2) Store base K/V and rank-32 coordinates per session in native.py for the last layer only. (3) Implement the rebuild-plus-latest-token publication step. (4) Run it on the Arc A380 or CPU, where re-prefill of DRock's ~7.6K-token median prompt (train.jsonl median 7594 tokens) is far slower than on an H200, so the saving per publication would be larger in absolute seconds. That saving only counts if DRock starts updating adapters during a live session.

## Limitations

Final-block-only adaptation with fixed K/V down-projections is a strong restriction, and its effect on task quality is unmeasured. All updates in the evaluation are Gaussian noise, not learned. Exactness holds only in exact arithmetic: in BF16 the continuation drifts from re-prefill by up to 5.59 in max logit at cadence 128, and greedy agreement was only checked on the tested cases. The single H200 setup says nothing about CPU or small-GPU behaviour. The runtime is process-local, with no durable recovery or distribution. No paged KV cache, and only standard RoPE. The two studies report decode overheads that disagree (19-24% vs 4.8%). No code release, so none of the numbers can be checked. The headline 68.98x covers the publication step alone; end-to-end saving including decoding is 3.90-16.24%.
