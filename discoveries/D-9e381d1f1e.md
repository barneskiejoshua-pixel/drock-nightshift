## Problem

Structured LLM output (tool calls, JSON, queries) breaks on one illegal token. Prompting makes valid output likely, never certain. Recomputing the legal set over a 128k-150k vocabulary every step is the speed problem.

## Technique

No engine is in the repo. The README specifies logit masking (illegal z_i set to -inf), regex to a DFA via Thompson NFA then subset construction, JSON Schema and EBNF to a pushdown automaton or an Earley recogniser, a byte trie of the tokenizer vocabulary, cached bitset masks for stack-independent states, jump-forward when the automaton has one continuation, and both a hand-written KV-cache sampler and a Hugging Face LogitsProcessor. Milestones M1-M7 are acceptance targets, not code.

## Foundation

Softmax over masked logits keeps relative probability among legal tokens only. Regular languages need a finite-state machine; nested JSON is context-free and needs a stack. A BPE token is legal only if the automaton can consume every byte. The speed design copies Outlines' per-state index (arXiv 2307.09702), XGrammar's context-independent tokens (arXiv 2411.15100), llguidance's vocabulary trie, and jump-forward decoding.

## Compute

The spec says a CPU-only Ubuntu box with 16 GB RAM and no GPU, Qwen2.5-0.5B-Instruct as the main model and GPT-2 (about 50k tokens) as a second tokenizer, versus Qwen's about 151k. Stated effort is three to four weeks part-time. Nothing is built, so nothing was run. DRock's i5-8400, 32 GB, and Arc A380 could host the 0.5B model, but there is no program to run.

## Reported

This repository reports no measurements. Planned gates, not results: greedy output token-identical to model.generate on 20 prompts; 1,000 regex samples match 100%; flat and nested JSON pass Pydantic model_validate_json at 100%; report mask latency, compile time, model calls saved, and tokens/s. Numbers it cites from other work, not measured here: OpenAI, Aug 2024, gpt-4-0613 under 40% on its complex-schema eval with prompting and 100% with constrained decoding; llguidance about 50 microseconds per token on a 128k vocabulary; XGrammar up to 100x (arXiv 2411.15100). The README also says a Python engine should lose to the Rust and C++ libraries, and that on CPU the model forward pass dominates wall clock, so end-to-end tokens/s would hide mask cost.

## Drock application

DRock already constrains actions with schema.json_schema and, when DROCK_GRAMMAR=gbnf, with gbnf.py sent to llama-server (model.py). This spec would replace that with a from-scratch Python masker. It does not. The only overlap is the existing claim that a name left out of the grammar cannot be sampled.

## Modifications

None worth porting: there is no compiler, trie, or sampler to adapt. A jump-forward pass on the existing llama.cpp grammar would be a different project, and this README supplies no implementation of the boundary re-tokenize step.

## Limitations

Syntax is not task success: the spec's own metrics split validity rate from answer quality and say the constraint can distort content. Structural tags (section 7) deliberately allow free text outside the grammar, so grammar exclusion is not a full boundary. Python is called out as not context-free. No stack-dependent mask timing, no seeds, and the author expects the Python engine to be slower than XGrammar, llguidance, and llama.cpp, which DRock's GBNF path already sits on. Key order inside a legal JSON object is untouched, so it does not speak to sampling reason before the action name.
