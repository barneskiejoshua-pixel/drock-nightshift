## Problem

Serving one large MoE model (Qwen3.8 Flash-Next) reliably and fast on old NVIDIA V100 (SM70) GPUs. V100 has no BF16 units, and mainline vLLM kernels mostly target newer GPUs.

## Technique

A vLLM fork, derived from 1Cat-vLLM. It runs on 4x V100 32 GB with tensor parallel 4 (TP4). Routed experts are 4-bit (AWQ g32 or NVFP4), PLE tables are FP8 and the rest is BF16 run as FP16. KV cache is E4M3. Evicted prefixes are kept in a CPU and NVMe KV tier. Speculative decoding uses MTP4 by default, or the optional DFlash2 drafter: 5 sliding-window layers, 8-token block, 2048-token window, draft width 7/3/4 depending on batch size. A release gate on the maintainer's server checks greedy-output consistency, 4 and 8 concurrent requests, multimodal input, CPU cache readback and 512K-token prompts.

## Foundation

Architecture: the vLLM paged-attention engine with CUDA kernels for SM70 (forks of flash-attention-v100 and flashinfer-sm70, plus csrc and a Rust component). Math: group-wise 4-bit weight quantization, FP8 KV cache, and the standard draft-and-verify speculative decoding.

## Compute

4 or more V100 32 GB cards (4 is the validated count), with NVLink or one PCIe switch with P2P. Host RAM: 80 GiB with the default pinned PLE table, 128 GiB recommended, and 32 GiB only with the experimental SSD PLE table (decode about 23-25% slower). Linux x86-64, glibc 2.34 or newer, Python 3.12, CUDA 12.8 driver. V100 16 GB, TP2 and TP8 are untested.

## Reported

These numbers are from the README and docs/dflash2.md and were not reproduced. Total output tok/s for 512-token responses, best of MTP4 and DFlash2. On 4x V100 PCIe with one switch (v0.1.2): 201 tok/s at 1 request, 275 at 2, 370 at 4, 509 at 8. On 4x V100-SXM2 with NVLink (community, v0.1.2 and v0.1.1 combined): 234, 260, 368, 525. Prefill at 8K/131K is 3,382/3,016 tok/s on PCIe and 4,680/4,037 on NVLink. GPU KV pool at 512K context with 8 concurrent requests (v0.1.4, Uncensored AWQ, E4M3 KV): 1.15M tokens with MTP4 and 1.37M with DFlash2. Quality against each BF16 parent on 66 records, as KL / top-1: AWQ 0.0214 / 97.1%, NVFP4 0.0303 / 96.4%, FP4-Local 0.0380 / 95.9%. A cached 32K-token prefix returns in 0.6 s from CPU and 1.5 s from NVMe after a restart, against 10.1 s to recompute. DFlash2 against MTP4: 1.30x on English code at 1 request, greedy, on different NVLink hardware; 0.93x at 8 mixed requests; 0.97x on real agent sessions with sampling (95% CI 0.90-1.01); slower on Chinese. No acceptance rates are reported.

## Drock application

Nothing direct. DRock runs small Qwen models in Ollama on an Intel Arc A380 with 6 GB, with no CUDA and no SM70. The kernels, the TP4 path and the 48 GiB PLE table do not apply. Two ideas could carry over. First, reuse the KV of the fixed system-prompt prefix across turns instead of recomputing it. Ollama already keeps the KV of the loaded context, so the first step is to measure whether DRock's prompt prefix stays byte-identical between turns. Second, their release gate checks that greedy output stays the same across concurrency, cache readback and long prompts. DRock could run the same check when it changes model, quantization or Ollama version.

## Modifications

For the gate idea: add a smoke check that runs a fixed set of prompts at temperature 0 and diffs the first action token or the parsed action against a stored baseline. Run it with and without a warm cache. For the prefix idea: no code until someone measures time-to-first-token with the current prompt layout against a layout with a stable prefix, using latency.jsonl.

## Limitations

Built for one model on V100 only. The quality numbers come from 66 unpublished records. DFlash2's gain disappears with sampling or 8 or more concurrent requests and reverses on Chinese text. There are no acceptance rates and no seeds. Some figures come from mixed versions or community hardware.
