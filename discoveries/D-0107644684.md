## Problem

Long-horizon agent tasks (about 150 tool calls, median context 92K tokens on DeepSWE) lose quality below 4 bits per weight when the quantizer is calibrated on short web text and judged by perplexity. The paper says published quantizations of Qwen3.8-27B at or below 3 bits per weight match BF16 on AIME but, in Unsloth's published results, solve at most 72% as many DeepSWE tasks as that harness's BF16.

## Technique

NariQ is post-training trellis quantization (QTIP bitshift code, codebook computed from the trellis state as in EXL3). It keeps the code and changes the objective: KL only on tokens the BF16 model wrote, with tool outputs left in the prefix; per-module width from a Hessian quadratic estimated by the weight gradient, scaled by the code's MSE (about 4x per bit) and allocated by dynamic programming on a multiple-choice knapsack; output rows in 16 bands by mean predicted probability with a 2-bit floor; scales and norm weights tuned on coding traces and general BF16 replies at 70:30. Matrices get randomized Hadamard rotations and YAQA-style two-sided rounding. The released core file ggml/src/ggml-trellis.cpp is the decoder (Hadamard/Paley, gathers, integer grid in [-126, 126]), not the allocator.

## Foundation

Second-order expansion of next-token KL around BF16 weights, plus QTIP trellis codes (cited 2-bit Gaussian MSE 0.069 versus rate-distortion 0.063), randomized Hadamard rotations, and YAQA input- and output-side rounding.

## Compute

Producing a file needs the BF16 Qwen3.8-27B checkpoint (paper: 55.6 GB including vision and MTP; README table lists BF16 at 53.8 GB) and gradients of the masked KL at several integer widths, then scale tuning. Released text GGUFs are 10.1, 8.4 and 6.8 GB at 3.0, 2.5 and 2.0 bpw, plus a shared 0.9 GB BF16 vision projector. README: a 24 GB NVIDIA GPU fits about 135K / 160K / 184K context with vision; the 262K window needs about 30 / 28 / 27 GB. Kernels are CUDA for compute capability 8.0+; the README says there are no AMD or Intel GPU kernels, the CPU path is slow for 27B, and the Windows GPU build was never run on a GPU. Measured decode is one session on an RTX PRO 6000.

## Reproducibility

Inference code is public: github.com/nari-labs/nari-llama.cpp, fork of ggml-org/llama.cpp, default branch nariq/b12431, release tag b12431-nariv0 (2026-11-20). Decoder is ggml/src/ggml-trellis.cpp; CUDA matmul is vendored libtrellis. conversion/trellis.py only packs a checkpoint that already has quant_method native_trellis; it does not quantize BF16 weights. No trainer, calibration traces, eval harness, or seeds are in the repo. Sampling is temperature 1.0 with one DeepSWE attempt. The Hugging Face card https://huggingface.co/nari-labs/Qwen3.8-27B-NariQ-GGUF failed to load after three tries, so the GGUF bytes were not checked here; the README says run.sh pins sha256. Paper HTML header says CC BY 4.0.

## Modifications

Using it on DRock would require a quantizer for the small Ollama Qwen models, a kernel for the Intel Arc A380 or a CPU path fast enough to matter, and a weight-plus-KV footprint under 6 GB. The release is a CUDA 8.0+ decoder for one 27B checkpoint, and the 2.0 bpw file is already 6.8 GB of text weights.

## Limitations

The paper limits itself to one model (Qwen3.8-27B), one agent harness (Claude Code), and says the 2.0 bpw file trails BF16 by 7.3 DeepSWE points and 11.7 AIME points. MTP is not quantized. The fork is tuned for one-GPU generation on SM120; other NVIDIA GPUs are slower, pre-Ampere falls back to CPU, and KV cache and activations are still full precision. Their 'level with BF16' at 3.0 and 2.5 bpw sits inside paired standard errors of about 3 points on 113 one-attempt tasks, so 47 versus 44 solved is inside that noise. Unsloth numbers are a different harness. Stock llama.cpp, Ollama and LM Studio cannot load the files. README: no NariQ kernels for AMD or Intel GPUs, Windows GPU never run, coded embedding lookups stay on the CPU, LoRA on these weights is rejected.
