## Problem

Granola-style AI meeting notes, but without a cloud service or a bot joining the call. It records mic and call audio on the user's machine, transcribes it, summarizes it, and answers questions across past meetings.

## Technique

An Electron desktop app. Speech-to-text is whisper.cpp (bundled whisper-server v1.9.5). Summaries and Q&A use a local open-weight LLM run through node-llama-cpp. Embeddings come from embeddinggemma-300m-q8_0 (512 dimensions) on chunks of about 300 words. Answers cite their source meetings. app/src/engine/llm.ts has a load ladder: default load, then gpuLayers fitContext at the minimum context, then gpuLayers 0, then a CPU-only llama instance. YOGURT_ENGINE_GPU=off turns the GPU off (comment: 'the graphics card crashed the engine before, on Windows or Linux'). It runs one warm-up evaluation at load so page-in cost is not paid on the first word. preload reads a shared conversation prefix ahead of time so later requests only read the new tokens. prefix.ts holds(): a tolerant prefix check that drops the first token and the last two, requires at least 8 tokens, and tries offsets 1 to 24. Temperature can be pinned so 'the same meeting names the same people each time'. Gemma 4 runs with reasoning:false, because a zero thought budget truncates instead of disabling.

## Foundation

Engineering, no new math. Whisper encoder-decoder ASR, quantized decoder LLMs (Q4_0, Q3_K_S, IQ2_XXS, MXFP4, some MoE), embedding retrieval, and llama.cpp KV-cache prefix reuse.

## Compute

8 GB RAM minimum. 16 GB or more allows a larger notes model. whisper-large-v3-turbo-q5_0 (0.57 GB) is gpuOnly with minMemGB 8; whisper-small-q5_1 and smaller run on CPU. catalog.json download sizes: qwen3-1.7b Q8_0 1.83 GB, gemma-4-e2b 3.35 GB, gemma-4-e4b 5.15 GB (marked starter), gpt-oss-20b 12.11 GB, gemma-4-26b-a4b 14.44 GB, gpt-oss-120b 63.39 GB. Platforms: Mac on Apple silicon (macOS 14.4+), Windows 10 2004+, Ubuntu 22.04+.

## Drock application

Small and indirect. (1) The GPU fallback ladder (full offload, then fit-context offload, then 0 GPU layers, then CPU) suits the Arc A380 with 6 GB. DRock runs Ollama, so the equivalent is retrying with a lower num_gpu or num_gpu=0 when the runner crashes. (2) Holding the system prompt prefix fixed so the KV cache gets reused, plus a warm-up call at load, could cut first-token latency. DRock's prompt_budget/latency.jsonl can measure that before and after. (3) The ~300-word chunk plus embedding Q&A with source links is a pattern for wiki.py or corpus search, if DRock does not already do it. Meeting transcription itself is outside DRock's scope.

## Modifications

Map the node-llama-cpp gpuLayers ladder onto Ollama options (num_gpu, num_ctx) in model.py, and trigger the fallback only on a runner crash or OOM, not on a slow response. For prefix reuse, the system prompt must be byte-stable across turns: no timestamps or per-turn text ahead of the dialogue. Ollama already reuses a matching prefix, so the work is keeping the prefix stable, not writing a cache.
