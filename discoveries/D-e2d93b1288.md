## Problem

Memory-first CPU inference for quantized GGUF models: how much resident memory can be avoided while still executing a real model correctly. RAM pressure is the target; throughput is secondary.

## Technique

mmap-backed GGUF weights (MAP_PRIVATE/PROT_READ, MADV_RANDOM default, WILLNEED/DONTNEED hints) so weights need no full heap copy; bounded tensor slices; paged KV cache with page_tokens and F32/F16/Q8 KV types; adaptive prefetch controller that changes look-ahead depth from useful/late/eviction/budget-skip/latency signals, requires 25% byte headroom before probing deeper and remembers rejected probes; LRU tensor cache and worker pool; batched prefill with reused scratch (batch 16 chosen empirically); RoPE tables grown only to used positions; Q4/Q8 AVX2/FMA kernels.

## Foundation

OS demand paging and page cache back the mapped weights, so RSS tracks touched pages rather than file size; 4-bit/8-bit quantization cuts weight bytes; fixed-token KV pages with F16/int8 storage bound attention-state bytes; adaptive lookahead is a feedback controller with explicit byte accounting for pending prefetch.

## Compute

C++20, CMake, Linux/POSIX (mmap, madvise, fcntl), GCC 14.2.0 with -O3 -march=native, AVX2/FMA paths, 1-5 CPU threads, no GPU. Tested on a virtualized AMD EPYC 9V74, 5 vCPU, ~5.9 GiB RAM, no swap, Linux x86-64; ARM64 cross-build/QEMU validation; PyPI wheel is a Linux x86-64 distribution shim. Inference requires GGUF general.architecture=llama; Qwen2 is parsed but not executed.

## Reported

README canonical A/B (results/openllama-7b-v2-ab/summary.json), OpenLLaMA 7B v2 Q4_0, same GGUF, CPU, pinned llama.cpp, repeated runs: peak RSS 3.80 GiB (3,982,168 KiB) vs 7.24 GiB (7,590,668 KiB), 47.54% reduction; prompt processing 2.917 ± 0.0015 tok/s vs 11.952 ± 0.0177; token generation 1.922 ± 0.0017 tok/s vs 7.966 ± 0.0338, so llama.cpp is ~4.10x and ~4.14x faster. Project says it is memory-first and does not claim to be faster. BENCHMARKS.md v0.3 (2026-08-20; EPYC 9V74 virtualized, 5 vCPU, ~5.9 GiB RAM, GCC 14.2.0, -O3 -march=native, 10 measured reps after warm-up): Q4_0 4096x4096 5-thread 1.134 ms / 29.576 GFLOP/s, Q8_0 0.769 ms / 43.633 GFLOP/s, F32 3.711 ms / 9.041 GFLOP/s; Q4_0 vs v0.2 up 3.59x at 4096x4096 and 2.93x at 11008x4096. Capacity test only: an 8 GiB sparse mapping traversed on ~5.9 GiB physical RAM at ~67 MiB peak process RSS.

## Drock application

Not as DRock's inference engine: DRock uses Ollama Qwen models; this executes only general.architecture=llama GGUF and explicitly does not implement Qwen2 inference. No Windows build path is shown (POSIX mmap/madvise), and the Arc A380 goes unused. The reusable piece is the measurement protocol: pin artifact hash and comparison commit, warm up, 5-10 measured reps, publish raw runs with mean/sd, state the throughput cost beside the memory win, and keep lowest-successful-ceiling distinct from a minimum requirement. That is a docs/harness change for DRock, not a runtime prototype.

## Limitations

Memory-first and explicitly slower: ~4.1x lower throughput than pinned llama.cpp in the headline A/B. Trained-model evidence only up to 7B; active prototype, stable release gated on evidence. Headline applies to one model, host and pinned runtime. The cgroup result is systems evidence, not a physical-RAM requirement; the sparse mapping is a capacity test, not a bandwidth claim. The microbenchmark host is virtualized with noise/non-monotonicity at 3-4 threads. No GPU path. README says the 7B table is generated from summary.json and must not be hand-edited.
