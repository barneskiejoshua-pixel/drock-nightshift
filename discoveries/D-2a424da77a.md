## Problem

Running ternary (BitNet b1.58) and low-bit quantized LLMs, embedders and rerankers from a C99 engine with no dependencies and an optional no-heap mode, on targets from microcontrollers up to Arm servers.

## Technique

Linear layers use ternary {-1,0,+1} weights packed 2 bits per weight, or a dense base-3 packing at 5 weights per byte (about 1.60 bits). Matmuls become integer add/subtract, with a scale per row or per group (g128/g96). An optional blockwise signed Walsh-Hadamard rotation is applied to the ternary inputs. INT4 and INT8 paths cover the non-ternary models. Qwen3.5 GGUFs are repacked to INT4 at load. Prefill decodes each weight row once per 64-token chunk and runs a blocked GEMM. Qwen3.5 is hybrid: 18 Gated DeltaNet linear-attention layers and 6 full GQA layers. The CPU paths are AVX2, NEON and OpenMP. An optional Vulkan compute path loads at runtime and needs no SDK to build. The byte-level BPE tokenizer is built in.

## Foundation

BitNet b1.58 ternary quantization with absmean-style scales per row or group. Hadamard rotation spreads outliers before low-bit quantization, the same idea as QuaRot. Linear attention (Gated DeltaNet) keeps O(1) state in its layers. Plain C99 kernels plus Vulkan compute shaders.

## Compute

CPU with AVX2 or NEON (an i5-8400 has AVX2). Vulkan is optional, and the A380 supports Vulkan, but the README has no Intel Arc results. Memory is the weights plus a state buffer that can come from a caller-supplied pool. The README gives about 35 MB of GPU memory per vision tile.

## Reported

These numbers are from the README; I ran nothing. Embedding latency on a GB10, CPU vs GPU: all-MiniLM-L6-v2 at 400 tokens, 36 ms vs 6 ms. bge-m3 at 100 tokens, 132 ms vs 34 ms. bge-m3 at 400 tokens, 615 ms vs 73 ms. The reranker (bge-reranker-v2-m3) takes about 0.26 s per 300-token pair on 20 Arm cores, with logits within 0.1 of HF fp32. GPU vs CPU embedding cosine is at least 0.9989. Vision GPU vs CPU cosine is 1.0000000 with max absolute difference about 1e-3. The tokenizer is claimed byte-exact against HuggingFace. Embeddings were checked by cosine against llama.cpp. The README states that Q8_0 GGUF keeps quality best and Q4_K_M degrades on long answers. It reports no text-generation tokens/s for any model or hardware, and no perplexity or task-accuracy numbers.

## Reproducibility

Code is public: a CMake build, the bitllm-run CLI, libbitllm.a/.so with a C API (bitllm.h), test suites and a GitHub workflow. No datasets or benchmark scripts with pinned model files are described for the latency numbers. Decoding is greedy, so seeds don't apply. The only hardware measured is a GB10 and 20 Arm cores, nothing like an i5-8400 or an A380. The repo has 2 stars and was last pushed 2026-11-07, so it is young and unreviewed.

## Drock application

Not the agent loop. DRock's Qwen models run in Ollama, which is already llama.cpp with AVX2 and quantized kernels, and nothing in this repo claims faster generation than that. The plausible use is narrow: an in-process embedder or reranker (bge-m3, MiniLM, bge-reranker-v2-m3) called through the C API from Python, for research/search.py ranking or the exemplar lookup in exemplars.py. That would remove one Ollama round trip. This is my opinion, untested.

## Modifications

DRock would need a ctypes binding to bitllm.h, a Windows build (the README lists Windows, but I didn't check CI coverage), and a test of the Vulkan path on Arc A380 drivers. It would also need a latency comparison against Ollama embeddings on the i5-8400, before and after, with both numbers. Ternary generation would need a BitNet-trained model, because ternarizing the existing Qwen weights after training would hurt quality badly.

## Limitations

There are no generation speed or quality numbers. The benchmarks are on hardware DRock doesn't have. The Qwen3.5 GGUF path is limited: no vision, no untied heads, fixed layer counts. Q4_K_M degrades on long answers, by the project's own note. The maintainer base is small and the code is new. BitNet gains need natively ternary models, and DRock's Qwen models aren't. The README doesn't say that Vulkan works on Intel Arc. None of the open problems is about inference speed or embedding quality.
